## 0. 三十秒版本

**这是什么**：一款 Windows 桌面软件（Tkinter），用户给出大纲/人设/世界观，软件调用 LLM（现役 `deepseek-v4-pro`）逐章生成超长篇小说，每章经**九维加权评分**（阈值 0.8），不达标则携带具体反馈迭代重写（上限 5 轮），达标后沉淀到项目与五层记忆。

**接手第一天做什么**：
1. 读本文 → 2. 跑 `python gui_main.py`（先 `set DEV_MODE=1`）→ 3. 跑 `python tests/_audit_e2e_normal.py`（离线全链路）→ 4. 读 `经验文档/12.人工验证与修复记录✅️.md` 的 V2.8/V2.13/V2.14 三节（评分体系的三层解剖）→ 5. 遇到问题先查本文第 10 节「高发缺陷模式目录」。

## 3. 核心业务：评分反馈循环（生成主链路）

### 3.1 端到端调用链（普通模式，逐文件）

```
GUI（生成页）
 → agents/novel_generation_service.py
     GenerationDataService.build_generation_context()   # 原始数据→生成上下文
     get_generation_service()._orchestrator.execute_novel_generation(config)
 → agents/plugins/novel_generation_agent.py
     payload 解包（键名契约见 §3.4）→ seed_previous_chapters(前5章)
 → plugins/novel-generator-v3/plugin.py  generate_chapter()
     步骤1  characters dict→list 归一化（约L470）
            _context_builder.build_optimized_prompt(...)      # 主prompt
            + 知识库/写作技巧注入段（V2.13起主路径才有！）
            + _ensure_chapter_end_marker()                    # 强制【本章完】要求
     步骤2-6 _iterative_generator.generate_with_iteration(prompt, validation_fn)
 → plugins/iterative-generator-v2/plugin.py  generate_with_iteration()
     循环≤5轮：发请求→评分→达标即停→否则 _build_feedback_text() 带具体
     反馈进下一轮（含AI腔具体短语、字数方向性纠偏[V2.14]）
     validation_fn = novel-generator 的 _validate_via_plugin →
 → plugins/quality-validator-v1/plugin.py  validate_with_weights()
     九维评分（真值来源，见§4）；不可用时降级 novel-generator 内联规则分
 → 达标：步骤7 剥标题行→更新前5章记忆→final_stats（判定分=上报分，V2.13）
 → services/project_manager.py  add_chapter()（沉淀，悬尾裁剪+补标记 V2.14）
```

### 3.2 五大不可破坏规则（实测全部生效）

1. 每章必须 `【本章完】`（生成由循环保障；续写/导入由 add_chapter 补齐，**补齐前先裁截断残句**）
2. 阈值 **0.8**，低于继续迭代
3. 迭代上限 **5 轮**
4. 九维权重不可改
5. 上下文记忆前 **5 章**（novel-generator 内 `previous_chapters`，会话恢复由 agent 层 seed）

实测行为参考：冷启动第 1 章通常 2-5 轮（实测 0.8135/2 轮达标）；有前章上下文的第 2 章起常 1 轮直过（0.805+）；单轮真实 API 耗时 60-130 秒。

### 3.3 判定分与上报分同源原则（V2.13 铁律）

迭代循环拿 validator 总分对照 0.8 判定停轮；`final_stats['weighted_total_score']` 必须取 `max(scores)` 与判定同源。**禁止事后用本地权重表对维度字典重算上报**——曾因此出现"循环判定达标停轮、上报却 0.7875"的自相矛盾。

### 3.4 跨层 payload 键名契约（历史断裂高发区）

| 生产方（编排器/服务） | 消费方（agent/插件） | 曾经的断裂 |
|---|---|---|
| `worldview` | `world_view` | 世界观从未到达生成插件（prompt 2353→4561字修复实证） |
| `style_profile` | `style` | 风格恒空，靠档案 tags 兜底填充 |
| `characters`（dict 以名为键） | List[Dict]（扁平或 V5 嵌套 basic_info） | 压缩器只认嵌套→人物块整体消失（V2.13） |
| `previous_chapters`/`previous_chapter_text` | seed_previous_chapters | 曾被接缝丢弃→会话恢复后无前文记忆 |

**任何新增跨层字段，先写契约测试再接线。**

## 4. 九维评分体系（真值来源与实现位置）

### 4.1 权重（锁定，配置在 config/validator_weights.yaml）

| 维度 | 权重 | 实现（quality-validator-v1/plugin.py） | 粒度说明 |
|------|:--:|---|---|
| character 人设 | 19% | `_score_character_consistency`(~L896) | 人名命中0.5基+性格词0.3+行为0.1+对话0.1；无人名命中兜底0.7 |
| style 风格 | 19% | `_score_style_consistency`(~L751) | 视角/语言/节奏关键词 |
| outline 大纲 | 13% | `_score_outline_compliance`(~L698) | 情节点关键词命中率**桶装分**（≥0.9→1.0/≥0.7→0.8/≥0.5→0.6/else 0.4） |
| worldview 世界观 | 12% | `_score_worldview_consistency`(~L954) | 核心词Top-30命中率（V2.7改，全词表交集数学趋零已废） |
| knowledge 知识库 | 8% | `_score_knowledge_reference`(~L1068) | 0.5基+召回0.2+被引用0.3；召回空→0.6 |
| writing_technique | 8% | `_score_text_quality` | |
| word_count 字数 | 8% | `_score_word_count`(~L652) | |
| context_coherence | 8% | | |
| ai_feeling AI感 | 5% | core/ai_feeling_detector.py | 与反AI指导共享词表 |

**治理原则（V6.3）**：数据为空=数据流断裂→应报错，不可用默认高分掩盖；用户未配置该维度→中性分 0.85。
**权重归属（ADR-010/011）**：加权计算只在插件层；GUI 只读显示，降级才用简单平均。

### 4.2 评分获取的正确姿势（V2.8 教训）

`novel-generator-v3._get_quality_validator()`：注册表优先 + **本地实例兜底**（importlib + initialize(PluginContext) + 缓存）。无头/独立进程注册表恒空，没有兜底时会永久静默降级到内联规则分（character 恒 0.5、style 恒 0.6 的低天花板，0.8 数学不可达，5 轮必跑满纯烧 API）。context-builder、quick/continuation 加载器同款模式。

### 4.3 量纲警告

续写（continuation-generator-v1）的多版本评分是**五维连贯性分**（连贯/风格匹配/字数/创意/可读），与九维加权分**不可比**。GUI 已标注"连贯评分"。给用户或文档呈现对比时必须区分量纲。

### 4.4 判读技巧：恒定的维度分=断裂信号

真实测量必有浮动。若某维度跨章恒定（如曾经的 knowledge 恒 0.6、character 恒 0.7），先怀疑该维度走了兜底路径而非真实测量，逐分支解剖（V2.13 靠这个信号挖出 9 处断裂）。

## 5. 生成路径全景（三条链）

### 5.1 普通模式
见 §3.1。上下文构建（prompt）由 context-builder-v1 `build_optimized_prompt` 负责：世界观压缩(≤2000tok)+风格压缩(≤1500tok)+**人物卡**（`_compress_character`，V2.13 起兼容扁平/嵌套双形态）+前章上下文+反AI指导+checklist。

### 5.2 专家模式（expert-novel-v1，7步学习闭环）
数据打包(回读 ExpertMemory 历史经验)→API 请求→九维评分→带反馈重试→输出最佳→沉淀 ExpertMemory→下次回读，越用越聪明。核心：`generate()`、`_build_iteration_feedback()`、`_enhance_request()`、`memory.py:ExpertMemory`。

### 5.3 续写（continuation-generator-v1）
前文概要提取→多版本并发生成（≤5版）→五维连贯评分→**一键保存永远取真实最高分**（best_index 被误标也会重找 max，harness `_audit_best_save.py` 7/7 保障）→ add_chapter 沉淀。

### 5.4 token 预算与故事完整性（V2.14/V2.15 铁律）

**上限的唯一真值来源是 provider 注册表**（core/online_provider.py 模型表）：deepseek-v4-pro / v4-flash 输出上限 **64000**。插件里不要二次硬编码过时数字（8192/4096 都曾是过时值）。

**DeepSeek 中文实测 ≈1.1 字/token**（《无极》实证：3162 字消耗约 2800 tokens）。预算公式按 1 字/token 保守估算：
- iterative-generator：`base=target/1.0; max=base*2.0; cap 64000`
- continuation：`TOKEN_RATIO=1.0; ×2.0; cap 64000`
（64K 上限下宽松预算无额外成本——费用按实际生成 token 计。）

**kwarg 静默丢弃陷阱（V2.15 修复）**：OnlineProvider.generate_text 曾只认 config 对象，`max_tokens=` kwargs 被静默丢弃（负数都能通过）。已修复为合并 kwargs 且两条路径都按注册表上限钳制。**探测契约真伪的技巧：喂非法值（如 -5），被接受=参数没生效。**

**故事完整性三级保障（V2.15）**：
1. 主保障：`_ensure_complete_ending`（iterative-generator 与 continuation-generator 各一份）——检测到末尾截断/标记盖悬句时，向模型追加"无缝续写至自然收束+【本章完】"的**真实补完请求**（含首尾重叠裁剪防复述）；失败才保留原文交评分判罚。
2. 判罚：评分环节对缺标记/字数异常降分驱动重写。
3. 最后兜底：add_chapter 补标记前悬尾裁剪（残句<120字回退最后完整句+warning）——仅防导入/遗留数据，正常链路不应触发。
**原则：完整性问题的正解是让模型把内容真正写完；裁剪与贴标记都是掩盖。**

## 6. 知识库子系统（V2.13 大修后的正确认知）

### 6.1 两个向量库！连错即全断（血泪教训）

| 库路径 | 用途 | 谁在用 |
|---|---|---|
| `data/knowledge_base` | **知识条目**向量（LanceDB 表 knowledge） | KnowledgeManager、KnowledgeRetriever（V2.13 修正后）、quality-validator 知识维度 |
| `data/vector_store` | **L2 温记忆**（章节向量等） | infrastructure/vector_store.get_vector_store() 全局单例 |

KnowledgeRetriever 曾用全局单例连到 `data/vector_store` → 知识检索上线即查错库、召回恒 0、知识维度恒兜底。任何新代码需要知识向量时，显式 `NovelVectorStore(db_path=<workspace>/data/knowledge_base)`。

### 6.2 数据流

```
JSON源 data/knowledge/<category>/<domain>.json
  {"category","domain","knowledge_points":[{"knowledge_id","title","content","keywords"...}]}
  knowledge_id 格式强校验：{category}-{domain}-{三位序号}（uuid后缀会被pydantic拒收）
   ↓ core/knowledge_manager.py create_knowledge/import_from_json（写JSON+同步向量）
LanceDB data/knowledge_base 表knowledge
   ↓ core/knowledge_retriever.py recall_knowledge(query, category, top_k, min_score=0.35)
   ↓ 相似度换算：LanceDB返回_distance(L2,越小越近)，sim = 1 - d/2（勿把距离当相似度！）
消费点①prompt注入：novel-generator._retrieve_knowledge(categories, query=章节大纲)
消费点②评分：quality-validator._score_knowledge_reference（genre=knowledge_categories[0]）
消费点③一致性：core/knowledge_recall.py check_knowledge_consistency（含LLM语义冲突检测，
              默认关闭 _enable_llm_check=False，按需开）
```

### 6.3 已知坑位

- `sync_vector_store()` 是**单向**的：只删向量库幽灵条目，不回填 JSON 新增——回填要自己调 `vector_store.add_knowledge`。
- `add_knowledge(metadata={})` 空 dict 会让 LanceDB 构造无字段 StructArray 直接 **panic**——已在 vector_store 归一为 `{"difficulty":"","tags":None}`（与表 schema `struct<difficulty:string, tags:null>` 一致）。
- LanceDB pandas 读回的 keywords 是 **numpy 数组**，`arr or []` 触发真值歧义异常，须显式 `list()`。
- 类别键是英文（xuanhuan/scifi/wuxia/history/urban/lingyi/writing_technique…），中文"玄幻"查不到。
- **各类别数据存量不均**：writing_technique 61 条最全；xuanhuan 曾是 0 条空壳（现 20 条 magic 域）；很多类别 JSON 目录存在但为空。批量补充用官方工具：
  `python tools/knowledge_generator_batch.py --category xuanhuan --count N`（LLM 生成，注意成本），生成后需回填向量库。

## 7. AI 服务与记忆

### 7.1 AI 服务

- 统一入口 `core/ai_service_manager.get_ai_service_manager()`，一切生成走它（harness mock 也在这一层打桩）。
- **现役模型：`deepseek-v4-pro`**（config.yaml `model` 字段 + API 响应回显双重确认），输出上限 64000 tokens；注册表另有 `deepseek-v4-flash`（同 64K，更快更廉，适合快捷创作草案/知识批量生成/一致性检测等高频低敏调用）。provider=DeepSeek；本地备选 Ollama `http://localhost:11434/v1`。
- API Key 加密存 `.secrets/`（`api_key: ENCRYPTED_IN_SECRETS_FILE`），**config.yaml 不入库、密钥永不明文**。提交前必须安全扫描 staged diff（pre-commit 钩子有基础检查）。
- **计费注意**：V4 Pro 的 usage.completion_tokens 包含推理 token（实测 max_tokens=5 的请求返回 completion_tokens=593）——估算成本时不要按可见文本长度算。
- Embedding：DeepSeek 不支持 → 自动降级本地 `all-MiniLM-L6-v2`（sentence_transformers_cache 缓存；离线环境设 `HF_HUB_OFFLINE=1`，gui 入口已处理）。

### 7.2 五层记忆（软件运行时，OpenClaw mem9）

L1 热 `core/session_state.py` ｜ L2 温 `infrastructure/vector_store.py`(data/vector_store) ｜ L3 冷 `core/git_notes_manager.py` ｜ L4 档案 `Memory-Novel Writing Assistant-Agent Pro/MEMORY.md` ｜ L5 云备份。WAL：`core/wal_manager.py`。

## 8. GUI 层要点（gui_main.py，约1.3万行）

### 8.1 铁律
- 业务逻辑下沉插件/服务层，GUI 只展示与编排；**不硬编码权重、不算评分、不判达标**（维度中文名映射取 quality-validator 的 `get_dimension_display_map()`/`get_dimension_attr_map()` 唯一真值）。
- 不要再往 gui_main.py 堆逻辑；新功能走"新增不改旧"。
- 用户明确要求：UI 外观不变、不卡顿。

### 8.2 线程模型
异步统一走 `ThreadPoolManager`（单例）；跨线程更新 UI 必须回 Tk 主线程（root.after）；无 mainloop 的 headless 环境（harness）用队列+泵模拟 after。

### 8.3 性能陷阱（已修，别复发）
- **emoji 首渲染 ~7 秒**（Tk 字体回退），每个新 emoji 再 ~1 秒 → 全局 emoji 拦截器覆盖 configure/StringVar.set/Treeview.insert，新 UI 文本别绕过它。
- **Treeview selection_set 事件回环**会无限循环冻死 UI → 高亮要幂等（selection 已是目标则跳过）+重入保护。
- 重型库（torch/lancedb/jieba）**惰性导入**，import 时间 4.6s→0.45s 的成果别用顶层 import 毁掉。

## 10. 高发缺陷模式目录（本项目全部实证，排查优先查这些）

1. **幽灵方法/符号 + 吞异常 = 永久静默降级**（3例实证：consistency_checker 的 get_llm_client、novel-generator 的 recall_by_category、KnowledgeManager 转换层属性）。except 打日志不等于问题被处理；导入/调用不存在符号的 try 块要重点搜。
2. **except 分支内的 NameError 顶替原始异常**（logger/Path 未定义于模块级）→ 表象是"全维度 0.5"这类整体性坏死。修一层再跑看下一层。
3. **跨层 payload 键名断裂**（§3.4 表）——新字段必须两端同改+契约测试。
4. **主路径缺功能、降级路径反而有**（知识注入只写在降级 prompt；validator 桥接只查空注册表）——桥接/降级架构必须实跑主路径验证，降级要打显眼日志。
5. **恒定的维度分**=兜底路径生效的信号（§4.4）。
6. **判定分与上报分不同源**（§3.3）。
7. **双向量库连错**（§6.1）。
8. **LanceDB 契约三坑**：空 metadata struct panic、_distance≠相似度、numpy 真值歧义（§6.3）。
9. **token 预算低估中文**、**上限硬编码过时**、**kwarg被静默丢弃**、**截断被补标记掩盖**（§5.4，四连坑）。
10. **LLM 输出类型与 pydantic 不符**（age=int、relationships=list）——边界归一化是必须层。
11. **多步生成上下文脱节**（四件套人名三样）——跨步骤传递关键实体（_extract_character_names_from_outline 模式）。
12. **lambda/闭包晚绑定异常变量 e**、**中文引号入 JSON**（用【】《》+json.dump）。
13. **签名鸡生蛋**：哈希不得包含签名载体与运行时可变目录（§2.1）。

## 11. 已知遗留与优化空间（诚实清单，按价值排序）

1. **大纲衰减**：快捷创作的大纲从第3章起"待定"，outline 维度约束力弱——治好它 outline 分才有真含金量。
2. **character 评分粒度粗**：人名命中+性格关键词字面匹配；"名字命中但关键词0"得 0.6，反而低于无人物兜底 0.7 的量纲倒挂。可引入语义匹配。
3. **句子完整性检测未进九维**：悬尾裁剪只在 add_chapter 防护；评分层加"截断/病句"检测可拦住第4章式硬伤。
4. **《无极》老四章是修复前产物**（"魏央"体系，与配置人设脱钩）：要设定贯通的成书需用现链路全量重生成。
5. gui_main.py 巨文件持续外迁（P0-V3：GenerationDataService 数据加工下沉）。
6. 知识库多数类别仍空/稀疏（§6.3），writing_technique 之外的覆盖需补。
7. 快捷四件套占位名（"角色3"）偶发。
8. outline_parser 存在另一加载副本报"0章"日志（主链不受影响，纯噪音待清）。
